# Инструкции для работы с проектом

## Назначение проекта

Проект предназначен для записи видеоданных с двух USB-камер
на борту безэкипажного катера.

Целевая платформа — Repka Pi под Linux.
Основной стек — Python, PyAV, V4L2, запись в Matroska (MKV).

Приоритеты:
1. хранение записей с камер в одной папке (recordings/date-time/cam-upper, recordings/date-time/cam-lower)
2. общая сессия
3. автозапуск
4. отслеживание записи через ноутбук или телефон (как лучше будет) (выводить статус работы)
5. управление (запуск, остановка) камер через ноутбук/телефон (что до этого выбрали)

Репозиторий содержит отдельные скрипты, а не установленный
Python-пакет. На момент первоначального изучения в нём
не было автоматизированных тестов, CI и манифеста зависимостей.
Перед работой проверь актуальное состояние.

- Не добавляй и не устанавливай зависимости без согласования.

## Целевая и локальная среды

### Целевая среда

Захват видео требует Linux/V4L2 и подключённых камер.

Используемые в текущих скриптах устройства:
- `/dev/video2` — cam_lower;
- `/dev/video4` — cam_upper.

Не считай эти пути универсальными: перед аппаратным
испытанием соответствие устройств камерам нужно проверить.

Пути, ожидаемые текущим `test_dual_pyav_queue.sh`:
- интерпретатор: `$HOME/recorder/venv-pyav14/bin/python`;
- рекордер: `$HOME/recorder/record_camera_pyav_queue.py`.

Изменения в локальном репозитории не попадают на Repka
автоматически.

Окружение на установке использует PyAV 14.
Не объявляй это доказанной минимальной или единственной
поддерживаемой версией без проверки зависимостей и API.

### Локальная среда

Текущая рабочая копия находится в Windows.

При первоначальном изучении `import av` локально завершался
ошибкой. Это состояние конкретного окружения, а не запрет
на локальную разработку и тестирование.

Без оборудования можно:
- изучать и изменять исходный код;
- проверять синтаксис;
- тестировать аппаратно-независимую логику;
- использовать временные файлы, фикстуры и заглушки.

Локальный синтаксический контроль:

    python -m compileall <file>

Эта команда не проверяет импорт зависимостей, захват видео,
работу потоков, производительность и взаимодействие с камерами.

Успешные проверки на Windows не подтверждают работу
Linux/V4L2, USB, накопителя и всей установки.


## Основные файлы

`record_camera_pyav_queue.py` — основной рекордер,
на который следует ориентироваться при текущей разработке.

Текущая архитектура:
- захват в основном потоке;
- запись MKV в рабочем потоке;
- ограниченная очередь сжатых видеопакетов.

Файлы `*_test.py` рассматриваются как более ранние эксперименты.
Не переноси в них исправления без отдельной задачи.

В ранних экспериментах используется
`Container.add_stream(template=...)`.
Основной рекордер использует `add_stream_from_template`
и проверяет наличие необходимого API.

Не делай общих выводов о совместимости версий PyAV
только по названиям методов: проверяй используемую версию,
сигнатуры и фактические ошибки.


## Команды запуска на целевой установке

Команды ниже предназначены для Linux-установки,
а не для локального PowerShell.

### Одна камера

    $HOME/recorder/venv-pyav14/bin/python \
      $HOME/recorder/record_camera_pyav_queue.py \
      --camera-id cam_lower \
      --device /dev/video2 \
      --seconds 10 \
      --segment-seconds 10

### Две камеры

    bash test_dual_pyav_queue.sh

Текущий shell-скрипт запускается без аргументов.
Длительность и порядок запуска проверяй по его актуальному коду;
не считай параметры этого примера постоянным требованием.

Предварительное условие, проверяемое shell-скриптом:
`exposure_dynamic_framerate` должен быть равен `0`
на обеих камерах.

Проверка:

    v4l2-ctl -d /dev/video2 --get-ctrl=exposure_dynamic_framerate
    v4l2-ctl -d /dev/video4 --get-ctrl=exposure_dynamic_framerate

Эти команды читают настройку.
Не изменяй настройки камер без согласования.


## Требования, которые необходимо сохранять

- Принятые пакеты нельзя молча отбрасывать.
- Переполнение очереди должно быть явно отражено
  в результате записи.
- Нельзя скрывать перегрузку за счёт пропуска кадров.
- Остановка должна обеспечивать корректное завершение
  потоков и закрытие файлов, насколько позволяет ситуация.
- Записанные пакеты должны сопоставляться с CSV-индексом.
- Идентификаторы `frame_id` должны оставаться последовательными
  в пределах сессии, включая переходы между сегментами.
- Временные метки приёма на хосте нельзя объявлять временем
  экспозиции камеры.
- Несовпадение результатов проверки нельзя выдавать
  за подтверждённую целостность.
- Ошибки записи и проверки должны быть видимы пользователю.


## Текущий контракт результатов

Следующее описывает существующее поведение.
Не меняй его без проверки потребителей данных.

- Каталог записи:
  `Path.home()/recordings/<prefix>_<camera>_<UTC timestamp>/`.
- На каждую сессию создаётся отдельный каталог;
  используется `mkdir(exist_ok=False)`.
- Метаданные: `session_metadata.json`.
- Индекс пакетов: `frames.csv`.
- JSON обновляется через временный файл и замену.
- Сегменты: `<camera_id>_segment_%04d.mkv`.
- Контейнер: Matroska.
- Временная шкала начинается заново для каждого сегмента.
- Текущая `time_base` выходного потока: `1/1000`.
- Вывод содержит строки с префиксами `Output: ` и `Status: `.
- Shell-скрипт использует последнюю строку `Output: `
  для определения каталога сессии.

Предполагаемый контракт кода завершения:
- `0` — только для результата `verified`;
- `1` — для остальных итоговых состояний.

При изменении завершения программы проверь все пути:
штатную остановку, сигналы, ошибки захвата, ошибки писателя
и ошибки верификации.

Состояния метаданных включают:
`starting`, `recording`, `verified`, `needs_review`, `failed`.


## Текущая реализация временных меток и проверки

- Выходные PTS строятся по монотонному времени приёма
  на хосте относительно начала сегмента.
- Используется миллисекундная шкала с округлением вниз.
- Исходные PTS/DTS/time_base сохраняются в CSV.
- `timestamp_is_exposure_time` имеет значение `false`.
- CSV содержит `packet_sha256` для сжатого содержимого пакета.
- Верификация повторно читает сегменты и сопоставляет
  содержимое, хеши, PTS, ключевые кадры, количество пакетов
  и порядок индексов.
- Сводка двухкамерного теста ожидает числовые значения
  `host_receive_monotonic_ns` в возрастающем порядке.
- Ограничения очереди задаются параметрами
  `--queue-frames` и `--queue-mib`.

Различай два случая:
1. Проверка выполнена, но обнаружено несовпадение.
2. Проверку не удалось завершить из-за исключения,
   ошибки чтения или демультиплексирования.

Не предполагай, что все исключения автоматически
превращаются в `needs_review`: проверяй обработчики в коде.

## Оформление файлов

- Сохраняй окончания строк LF, особенно в shell-скриптах.
- Не допускай массового изменения окончаний строк.
- Учитывай, что при первоначальной проверке
  `core.autocrlf` имел значение `true`.
- Сохраняй существующий язык консольных сообщений
  в изменяемом файле.
- Не меняй текст, используемый машинным разбором,
  ради стилистических улучшений.
