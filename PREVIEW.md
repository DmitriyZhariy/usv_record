# Просмотр двух камер (этап 1)

Веб-страница на Repka с двумя MJPEG-изображениями для настройки фокуса
и положения камер. Только просмотр: записи не создаются, формат записей
и основной рекордер не изменяются.

Реализация — один файл `preview_dual_mjpeg.py`. Захват идёт через PyAV/V4L2,
HTTP-сервер и страница используют только стандартную библиотеку Python.
Внешних JS/CSS нет: страница работает без доступа в интернет.

## Что делает

- одновременно открывает обе камеры и показывает их в браузере;
- подписи «Левая камера» (`cam_left`, `/dev/video2`) и
  «Правая камера» (`cam_right`, `/dev/video4`);
- в двух колонках левая камера слева, правая справа; при одной колонке
  левая сверху, правая снизу;
- целевая частота **публикации** задаётся `--fps` (по умолчанию 8 кадров/с
  на камеру); фактическая частота захвата определяется камерой и показывается
  в `/status.json` как измеренная;
- масштаб на клиенте: `Fit`, `1:1`, `200%`, `400%`, перетаскивание мышью;
- не накапливает кадры в приложении: хранится только последний кадр;
- показывает свежесть кадра на сервере и время с последнего кадра в браузере;
- показывает ошибки камеры и отсутствие свежих кадров;
- при остановке закрывает контейнеры и освобождает устройства.

## Чего не делает

- не пишет видео и не меняет `~/recordings`;
- не меняет экспозицию и настройки камеры через `v4l2-ctl`;
  открывает тот же режим, что и рекордер (`mjpeg 1280x720@60`);
- не использует WebRTC, Docker и внешние библиотеки;
- не настраивает сеть, файрвол и автозапуск;
- не публикуется в интернет и не имеет авторизации;
- не запускает декодирование/перекодирование как резервный путь
  (см. «Диагностика», если прямой MJPEG не работает).

## Требования

- Repka под Linux с V4L2 и подключёнными камерами.
- Python 3.7+ (используется `http.server.ThreadingHTTPServer`).
  Проверить: `python3 --version`.
- PyAV (`av`) — уже используется рекордером и лежит в
  `$HOME/recorder/venv-pyav14`. В режиме `--fake-cameras` PyAV не нужен.
- Новые пакеты не требуются. Точный список импортов:
  - сторонние: `av` (PyAV, только реальный захват);
  - стандартная библиотека: `argparse`, `base64`, `errno`, `json`, `os`,
    `signal`, `socket`, `sys`, `threading`, `time`, `traceback`,
    `collections`, `datetime`, `http.server`, `pathlib`, `urllib.parse`.
- `fcntl` — только на Linux, для lock-файла; на Windows недоступен и
  блокировка второго экземпляра не работает.

Проверка версии PyAV на Repka (только чтение):

    $HOME/recorder/venv-pyav14/bin/python -c "import av; print(av.__version__)"

## Копирование на Repka

Команды выполняет пользователь; агент к Repka не подключается.
Из корня репозитория на Windows:

    scp preview_dual_mjpeg.py '<user>@<repka-ip>:~/recorder/'
    scp PREVIEW.md '<user>@<repka-ip>:~/recorder/'

Каталог `$HOME/recorder` уже ожидается текущим `test_dual_pyav_queue.sh`.
Тесты `tests/` на Repka копировать не нужно.

## Запуск и остановка

Перед запуском проверить соответствие устройств (только чтение, настройки
не меняются):

    v4l2-ctl --list-devices
    v4l2-ctl -d /dev/video2 --get-ctrl=exposure_dynamic_framerate
    v4l2-ctl -d /dev/video4 --get-ctrl=exposure_dynamic_framerate

Запуск в foreground (автозапуск не настраивается):

    cd $HOME/recorder
    venv-pyav14/bin/python preview_dual_mjpeg.py \
      --fps 8 --port 8088 \
      --device-left /dev/video2 --device-right /dev/video4

Страница:

    http://<ip-repka>:8088/

Остановка: `Ctrl+C` (SIGINT) или SIGTERM. После остановки в журнале должно
быть «Потоки захвата остановлены, контейнеры закрыты».

Полезные флаги:

| Флаг | Назначение |
|---|---|
| `--fps` | целевая частота публикации на камеру (по умолчанию 8) |
| `--port` | порт HTTP (по умолчанию 8088) |
| `--host` | адрес прослушивания (по умолчанию `0.0.0.0`) |
| `--device-left`, `--device-right` | устройства камер (`/dev/video2`, `/dev/video4`) |
| `--max-clients` | максимум одновременных MJPEG-потоков (по умолчанию 8) |
| `--fake-cameras` | тестовые JPEG без обращения к устройствам |
| `--fake-capture-fps` | частота генерации в тестовом режиме |
| `--no-lock` | не брать lock-файл второго экземпляра |

Сервис не публикуется в интернет. Доступ — только из локальной сети;
настройка сети и файрвола не входит в задачу.

## Как устроен поток кадров

- На камеру — один поток захвата, который непрерывно читает `demux()`
  (чтобы не рос буфер V4L2) и публикует кадр не чаще `--fps`.
- Камера открывается с теми же опциями, что у рекордера:
  `v4l2`, `input_format=mjpeg`, `1280x720`, `60`. Это запрос режима при
  открытии, а не изменение экспозиции или иных настроек через `v4l2-ctl`.
  Если камера согласовала другой режим, он виден в `/status.json`.
- Промежуточные пакеты в режиме просмотра отбрасываются: это не запись,
  ограничения рекордера («не отбрасывать принятые пакеты») не затрагиваются.
- Хранится ровно один последний кадр. Клиент получает кадр новее своего
  последнего; догнать «очередь» невозможно, потому что её нет.
- Запись в сокет выполняется в потоке клиента, вне блокировки кадра,
  поэтому медленный клиент не задерживает захват.
- Размер буфера отправки ограничен (`SO_SNDBUF`, 64 КиБ), чтобы уменьшить
  объём уже отправленных, но ещё не прочитанных кадров.
- Число одновременных потоков ограничено `--max-clients`; сверх лимита —
  HTTP 503.

### Свежесть на сервере и визуальная задержка

`last_frame_age_s` в `/status.json` — возраст последнего опубликованного
кадра **на сервере**. Это не визуальная задержка.

Визуальная задержка = серверная свежесть + передача по сети + буферы
TCP/браузера + декодирование и отрисовка. На странице отдельно показаны
«сервер» и «браузер»; ни одно из чисел не гарантирует задержку на экране.
Фактические частоту и задержку можно утверждать только после измерений
на Repka.

## Завершение и его ограничения

- Обработчики SIGINT/SIGTERM только выставляют событие останова.
- Главный поток ждёт событие, затем вызывает `server.shutdown()` из главного
  потока (не из потока `serve_forever()`), закрывает сервер и вызывает
  `app.stop()`.
- `app.stop()` ждёт каждый поток захвата с общим бюджетом 4 с, бесконечного
  `join()` нет. Контейнер закрывает тот поток, который его открыл, в `finally`.
- Блокирующий `demux()` не обязан прерываться по событию. Если камера
  зависла или отключена, поток может не успеть завершиться за 4 с.
  В этом случае печатается предупреждение, код возврата — `1`.
  Потоки захвата объявлены daemon: процесс завершится, файловые дескрипторы
  освободит ОС, но корректность закрытия контейнера в таком сценарии
  не гарантируется. Это ограничение, а не «нормальный» путь остановки.
- HTTP-потоки тоже daemon и не удерживают процесс.

Проверка освобождения устройств:

    fuser -v /dev/video2 /dev/video4

Если `fuser` не установлен:

    ls -l /proc/*/fd 2>/dev/null | grep -E 'video(2|4)'

## Совместимость с рекордером

Просмотр и запись — взаимоисключающие режимы. Просмотр не создаёт записи;
рекордер о просмотрщике не знает.

- Lock-файл (`~/.cache/usv_record/preview.lock`) защищает **только** от
  второго экземпляра просмотрщика. У wrapper записи свой отдельный
  lock-файл; общий менеджер режимов не вводится.
- Перед запуском записи просмотр останавливается вручную.
- Проверка `/proc/*/fd` — необязательная диагностика. Она не гарантирует
  отсутствие конфликта: другой процесс может открыть камеру сразу после
  проверки.
- Ошибки `av.open()` и начала захвата обрабатываются: камера получает
  состояние `error`, текст виден на странице и в журнале, вторая камера
  продолжает работать.
- Не запускайте просмотр при работающем рекордере и наоборот. Если камера
  занята, ожидайте явную ошибку, а не совместную работу.

## Диагностика

- `GET /status.json` — состояние камер, счётчики, измеренные частоты,
  свежесть, ошибки, число клиентов.
- `GET /diagnostics/frame.jpg?camera=left` (или `right`) — последний
  опубликованный пакет как файл JPEG (заголовок `X-Frame-Age-Ms`).
  Можно сохранить:

      curl -o frame_left.jpg http://<ip-repka>:8088/diagnostics/frame.jpg?camera=left
      file frame_left.jpg

  Если файл открывается как изображение, а поток в браузере нет — проблема
  в HTTP-потоке/браузере. Если файл не является корректным JPEG — камера
  отдаёт не самостоятельный JPEG; автоматического перекодирования нет.
  Это нужно зафиксировать и согласовать отдельно.
- Проверка `has_jpeg_markers()` в коде смотрит только SOI/EOI и не является
  проверкой корректности изображения.

## Локальные проверки (Windows, без камер)

    python -m compileall preview_dual_mjpeg.py tests/test_preview_core.py
    python -m unittest discover -s tests -v

Ручная проверка страницы без камер:

    python preview_dual_mjpeg.py --fake-cameras --host 127.0.0.1 --port 8099 --fps 5
    # открыть http://127.0.0.1:8099/

Тестовый режим отдаёт настоящие JPEG (SOI/EOI/SOF, декодируются браузером),
не открывает устройства и не импортирует PyAV. Эти проверки не подтверждают
частоту, задержку, работу V4L2/USB и освобождение устройств на Repka.

## Чек-лист аппаратной приёмки

1. `v4l2-ctl --list-devices`: `/dev/video2` — левая, `/dev/video4` — правая.
   Если соответствие другое, использовать `--device-left/--device-right`,
   настройки камер не менять.
2. Зафиксировать версии: `python3 --version`,
   `venv-pyav14/bin/python -c "import av; print(av.__version__)"`.
3. Запустить просмотр; в журнале обе камеры открыты как `mjpeg 1280x720`.
4. С ноутбука: слева изображение физически левой камеры, справа — правой;
   подписи, устройство, статус и диагностический JPEG (`camera=left|right`)
   совпадают с изображением. В `/status.json` `state=running`,
   `last_frame_age_s` мало́, измеренная частота захвата видна.
5. Сузить окно: одна колонка, левая камера сверху, правая снизу.
6. Проверить `1:1`, `200%`, `400%` и перетаскивание; оценить фокус.
7. Открыть страницу с телефона в той же локальной сети.
8. Медленный клиент: `curl --limit-rate 20k -o /dev/null
   http://<ip-repka>:8088/stream/left.mjpg`. Убедиться, что серверная
   свежесть и частота публикации не деградируют; визуальную задержку этого
   клиента измерять отдельно.
9. Отключить одну камеру (если это безопасно): её плашка краснеет, вторая
   продолжает работать. Зафиксировать фактическое поведение после возврата.
10. `Ctrl+C`: в журнале сообщение об остановке потоков и закрытии контейнеров,
    код возврата не проверяется при интерактивном запуске.
11. `fuser -v /dev/video2 /dev/video4` (или `ls -l /proc/*/fd`): устройств
    нет в чужих дескрипторах.
12. Сразу запустить запись обеих камер (`record_dual_session.py`) и убедиться,
    что она стартует; затем остановить.
13. Зафиксировать `top`/`htop` (CPU, память) при 8 к/с и при медленном
    клиенте. Не переносить эти цифры на другие режимы.

## Непроверенные ограничения

- Фактическая частота публикации, задержка, CPU и температура на Repka
  не измерялись.
- Не подтверждено, что V4L2/MJPEG отдаёт пакеты, пригодные для прямой отдачи
  в браузер без перекодирования; проверяется диагностическим JPEG.
- Поведение при зависшем `demux()` и корректность закрытия контейнера в этом
  случае не проверялись на железе.
- Число одновременных клиентов и поведение на телефонах не измерялись;
  MJPEG без авторизации и шифрования рассчитан только на локальную сеть.
- Соответствие `/dev/video2`/`/dev/video4` камерам зависит от установки.
- Совместимость с работающим рекордером не гарантируется; режимы
  взаимоисключающие.
