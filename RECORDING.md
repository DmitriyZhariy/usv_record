# Запись обеих камер в общую сессию

Один запуск `record_dual_session.py` создаёт общий каталог сессии
и запускает два существующих рекордера
`record_camera_pyav_queue.py` — по одному на камеру. Захват, очередь,
сегментация, CSV, метаданные, хеши и проверка целостности не
переписываются: wrapper только управляет каталогами и процессами.

## Соответствие камер

| Физическое положение | Устройство | `--camera-id` | Каталог | Подпись |
|---|---|---|---|---|
| Левая | `/dev/video2` | `cam_left` | `cam-left/` | «Левая камера» |
| Правая | `/dev/video4` | `cam_right` | `cam-right/` | «Правая камера» |

Привязка устройств не меняется. Если на конкретной установке
соответствие другое, используйте `--device-left`/`--device-right`;
не меняйте udev, USB и параметры захвата без отдельного согласования.

## Структура сессии

    recordings/<UTC timestamp>/
        cam-left/
            session_metadata.json
            frames.csv
            cam_left_segment_0000.mkv
            ...
        cam-right/
            session_metadata.json
            frames.csv
            cam_right_segment_0000.mkv
            ...
        cam-left.log
        cam-right.log

- Корень по умолчанию — `~/recordings`; его можно изменить
  через `--output-root`.
- Wrapper создаёт каталог `<output-root>/<timestamp>/` и файлы логов
  в нём; каталоги камер он не создаёт.
- Каждый рекордер сам создаёт свой `cam-left/` или `cam-right/`
  через `mkdir(exist_ok=False)`.
- Общего `session.json` в корне сессии нет.
- Старые записи не читаются, не переименовываются и не удаляются.

## Запуск на Repka

Остановите просмотр: просмотр и запись — взаимоисключающие режимы.
Изменения с локальной машины не попадают на Repka автоматически.
Для управления с ноутбука или телефона используйте веб-панель
`control_panel.py` (см. `PANEL.md`); wrapper можно запускать и напрямую.

    cd $HOME/recorder
    venv-pyav14/bin/python record_dual_session.py \
      --seconds 20 --segment-seconds 10

`--seconds 0` означает «до остановки оператором» (`Ctrl+C`/SIGTERM).
Значение по умолчанию остаётся 35.

Обе камеры запускаются одной командой. Wrapper печатает:

    Output: /home/<user>/recordings/20261024_123045_123456
    cam_left: /dev/video2 -> .../cam-left
    cam_right: /dev/video4 -> .../cam-right

`Output: ` в выводе wrapper — это корень сессии. В логах каждой
камеры `Output: ` указывает уже на её подкаталог.

### Параметры

| Параметр | Назначение |
|---|---|
| `--output-root` | корень сессий, по умолчанию `~/recordings` |
| `--device-left` | устройство левой камеры, по умолчанию `/dev/video2` |
| `--device-right` | устройство правой камеры, по умолчанию `/dev/video4` |
| `--seconds` | длительность записи каждой камеры; `0` — до остановки оператором |
| `--segment-seconds` | длина сегмента MKV |
| `--queue-frames`, `--queue-mib` | ограничения очереди, передаются рекордеру |
| `--min-free-mib` | порог свободного места для запуска (по умолчанию 4096 MiB) |
| `--critical-free-mib` | порог штатной остановки (по умолчанию 1024 MiB) |
| `--v4l2-ctl` | путь к `v4l2-ctl` для проверок |
| `--lock-file` | lock второго экземпляра wrapper |

Параметры камер, режим `mjpeg 1280x720@60`, временные метки, политика
очереди и верификация остаются такими же, как у одиночного рекордера.

## Предпусковые проверки и свободное место

До создания сессии wrapper проверяет каталог `--output-root`, требует
не меньше `--min-free-mib` свободного места, проверяет занятость
устройств по `/proc`, затем устанавливает
`exposure_dynamic_framerate=0` на обеих камерах и читает значение
обратно. Другие настройки камер не изменяются. Команды `v4l2-ctl`
выполняются с ограниченным timeout и `shell=False`. Ошибка установки,
ошибка чтения или значение не `0` на любой камере отменяют запуск
обеих записей: сессия не создаётся, код возврата `1`, печатается
`Preflight failed: ...`.

Во время записи место проверяется каждые 5 секунд. Ниже
`--critical-free-mib` запись штатно останавливается с причиной
`low_disk_reserve`; исключение `disk_usage` даёт причину
`disk_check_failed` и не завершает монитор. Wrapper печатает
`Stop reason: ...`. Данные не удаляются.

Проверка занятости через `/proc` — диагностика, а не гарантия
взаимного исключения: процесс может открыть устройство сразу после
проверки. Второй экземпляр wrapper по-прежнему ограничен lock-файлом.

## Одиночный рекордер

Без `--output-dir` рекордер создаёт
`<output-root>/queued_<camera>_<UTC timestamp>/`, как раньше, но с
новыми идентификаторами:

    $HOME/recorder/venv-pyav14/bin/python \
      $HOME/recorder/record_camera_pyav_queue.py \
      --camera-id cam_left --device /dev/video2 \
      --seconds 10 --segment-seconds 10

`--output-dir` задаёт точный каталог камеры. Он должен отсутствовать,
даже если пуст. `--output-dir` и `--output-root` взаимоисключающие:
при совместном использовании рекордер завершается с ошибкой.

## Защита от перезаписи

- Имя сессии — UTC `%Y%m%d_%H%M%S_%f`.
- При совпадении имени wrapper добавляет `_01`, `_02`, … и не трогает
  существующий каталог.
- Рекордер отказывается использовать существующий `--output-dir`
  и возвращает ненулевой код.
- Повторный запуск создаёт новую сессию; файлы предыдущей не меняются.

## Логи и коды завершения

Каждый рекордер пишет свой stdout/stderr в
`<session>/cam-left.log` или `<session>/cam-right.log`.
Общий вывод wrapper остаётся в терминале.

- Wrapper: `0` — оба рекордера вернули `0` (обе записи `verified`);
  `1` — ошибка запуска, камеры, проверки, таймаут или
  принудительное завершение.
- Рекордер: `0` — только `verified`, иначе `1` (ошибки разбора
  аргументов `argparse` дают `2`).
- Остановка оператором (`Ctrl+C`/SIGTERM): wrapper передаёт сигнал
  обоим процессам. Если обе записи после остановки прошли проверку,
  код может быть `0`; причина остановки печатается отдельно.
  Это не означает, что заданная длительность была выдержана.
- Если процесс не завершился за отведённое время, wrapper применяет
  SIGKILL, обязательно делает `wait()` и сообщает о принудительном
  завершении; это ошибка с кодом `1`.
- При ошибке каталог сессии, метаданные и логи не удаляются:
  пользователь видит путь и причину.

Рекордеры запускаются с `start_new_session=True` на Linux, поэтому
`Ctrl+C` терминала не дублируется в дочерние процессы: остановкой
управляет wrapper.

## Ограничения

- Wrapper защищает только от второго экземпляра wrapper
  (`~/.cache/usv_record/record_dual.lock`). Взаимоисключение просмотра
  и записи обеспечивает веб-панель `control_panel.py`; при прямом
  запуске из CLI просмотр нужно останавливать вручную.
- Веб-панель и автозапуск описаны в `PANEL.md`. Панель запускает
  только wrapper; отдельного сервиса записи и автоматического
  восстановления записи нет.
- Локально на Windows без PyAV и камер проверяются только логика
  каталогов, команд и управление процессами-заглушками.
- Проверки монтирования внешнего накопителя нет: если он не смонтирован,
  `--output-root` может оказаться на корневой ФС, и wrapper этого не
  обнаружит. Монтирование проверяет оператор (`findmnt --target ...`).
- Исторические `record_*_test.py` остаются автономными экспериментами
  со старыми именами; актуальные скрипты их не вызывают.

## Копирование на Repka

Команды выполняет пользователь из корня репозитория на Windows
(PowerShell). Кавычки не дают локальному `$HOME` подставиться вместо
удалённого пути:

    scp record_camera_pyav_queue.py record_dual_session.py `
        record_preflight.py preview_dual_mjpeg.py `
        control_panel.py panel_page.py `
        test_dual_pyav_queue.sh PREVIEW.md RECORDING.md PANEL.md `
        '<user>@<repka-ip>:~/recorder/'

Каталог `~/recorder` уже ожидается `test_dual_pyav_queue.sh`.
Каталог `tests/` на Repka копировать не нужно: он предназначен для
локальных проверок без камер.

## Локальные проверки

    python -m compileall record_camera_pyav_queue.py record_dual_session.py \
      record_preflight.py preview_dual_mjpeg.py control_panel.py \
      panel_page.py tests
    python -m unittest discover -s tests -v
    bash -n test_dual_pyav_queue.sh

Тесты не требуют PyAV и камер. Linux-специфичные проверки
(`start_new_session`, `flock`) помечены `skipUnless` и на Windows
пропускаются. Успех на Windows не подтверждает работу V4L2,
USB, накопителя и всей установки.

## Аппаратная приёмка на Repka

1. Остановить просмотр, проверить `fuser -v /dev/video2 /dev/video4`.
2. Убедиться, что накопитель смонтирован: `findmnt --target ~/recordings`.
   Автоматической проверки монтирования нет; без накопителя запись
   уйдёт на корневую ФС.
3. Запустить `record_dual_session.py` (или запись из веб-панели):
   wrapper сам установит `exposure_dynamic_framerate=0` на обеих
   камерах и прочитает значение обратно.
4. Убедиться, что создана одна сессия с `cam-left/` и `cam-right/`,
   в каждом каталоге есть `session_metadata.json`, `frames.csv`
   и сегменты; оба статуса `verified`, коды `0`.
5. Повторно запустить запись; сравнить sha256/mtime файлов предыдущей
   сессии — они не должны измениться.
6. Запустить `bash test_dual_pyav_queue.sh`; проверить сводку по
   `cam-left`/`cam-right` и итоговый код `0`.
7. Во время записи нажать `Ctrl+C`: оба процесса завершаются,
   устройства освобождаются, после этого снова запускается просмотр.
