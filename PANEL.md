# Веб-панель просмотра и записи двух камер

> Исторический документ. Актуальное руководство по установке:
> [docs/HANDOVER_RU.md](docs/HANDOVER_RU.md). Отдельные разделы могут
> описывать прежние порт и пути.

`control_panel.py` — одна страница на порту 8088 для ноутбука или
телефона. Панель не захватывает видео и не пишет файлы сама:

- просмотр выполняет `preview_dual_mjpeg.PreviewApp` в процессе панели;
- запись выполняет `record_dual_session.py` отдельным процессом;
- предпусковые проверки и контроль свободного места находятся
  в wrapper, поэтому прямой запуск wrapper из CLI их не обходит.

После загрузки панель находится в состоянии `idle`: камеры не
открываются, запись не начинается. Запись запускает только оператор.

Просмотр и запись взаимоисключающие. Команда «Начать запись» сначала
останавливает просмотр и только после этого запускает wrapper.
Во время записи изображение с камер в панели не показывается.

## Профили обеих камер (этап B)

Панель использует единый профиль: `mode`, `exposure_dynamic_framerate`,
`duration_seconds`. Перечень семи режимов MJPG задаёт `record_profiles.py`.
YUYV не используется. Режим считается доступным, только если подтверждён
в выводе `v4l2-ctl --list-formats-ext` обеих камер. Это проверка заявленной
поддержки, а не гарантия совместной производительности USB.

При запуске панели камеры для захвата не открываются и запись не начинается.
В фоне выполняется read-only перечисление режимов. До завершения этой
проверки запуск просмотра и записи запрещён. Ошибка видна в статусе;
повторить проверку можно кнопкой «Проверить режимы», только в `idle`.

Порядок работы:
1. Дождаться результата перечисления режимов в `idle`.
2. Выбрать режим, dynamic и длительность.
3. Нажать «Применить профиль». Это сохраняет выбор в памяти, не меняя камер.
4. Запустить просмотр или запись. Пока есть неприменённый выбор, кнопки
   запуска в этой вкладке отключены; сервер запускает только сохранённый профиль.
5. Перед изменением профиля остановить просмотр/запись и дождаться `idle`.

Список длительностей: 0 (до остановки), 10, 30, 300, 600, 1800, 3600 секунд.
Через API допустимы и другие конечные неотрицательные длительности.
Начальный профиль — 1280x720@60, dynamic=0; длительность берётся из
`--record-seconds` (default 0). Нестандартная начальная длительность
добавляется в список страницы. После перезапуска выбор не сохраняется.

При принятии команды запуска фиксируется копия профиля. Изменение
запрещено в `starting`, `preview`, `recording`, `stopping`, `error`,
при завершении панели и при незавершённых потоках просмотра.
Несколько вкладок работают с одним серверным профилем; интерфейс показывает
изменение, сделанное в другой вкладке. Черновик выбора не теряется при
обычном опросе статуса, если серверный профиль не изменился.

Перед реальным просмотром проверяется диагностическая занятость устройств,
снова перечисляются режимы, затем выставляется выбранный dynamic на обеих
камерах и читается обратно. При ошибке захват не запускается. Диагностика
занятости не заменяет эксклюзивную блокировку от всех сторонних программ.
Перед записью просмотр штатно останавливается; выбранные width/height/FPS,
dynamic и длительность передаются wrapper, где остаются свежие preflight
проверки. Установка dynamic при просмотре — намеренное изменение настройки
камер по команде оператора, а не свойство кнопки применения профиля.

Dynamic=1 разрешает снижение частоты, но не гарантирует его или рост яркости.
Уменьшенный измеренный темп сам по себе не означает ошибку целостности.
Страница различает запрошенный FPS захвата, темп входящих пакетов и темп
публикации просмотра. `--fps` панели ограничивает публикацию, не запись.
Итоговый `measured_capture_fps` рекордера вычисляется при завершении; до
этого поле может быть null. Ни один из этих показателей не является
временем экспозиции или доказательством синхронизации/отсутствия потерь
до приложения. Номинальный FPS после открытия не подтверждён: null.

HTTP-контракт (существующие token/Origin-проверки сохранены):

| Запрос | Ответ |
|---|---|
| `GET /api/status` | 200; профиль, варианты, причины, блокировка и поддержка |
| `POST /api/profile/apply` | 200; JSON ровно с тремя полями профиля |
| `POST /api/profile/check` | 202; асинхронная read-only проверка |

Пример JSON: `{"mode":"1280x720@30","exposure_dynamic_framerate":1,"duration_seconds":20}`.
Ошибочные типы, неизвестные/пропущенные поля — 400; недоступное состояние
или неподтверждённый режим — 409; завершение панели — 503.
Все API требуют `X-USV-Token`; POST также проверяет Origin/тип и размер тела.

В `/api/status` добавлены `profile`, `profile_details`, `profile_options`,
`profile_durations`, `profile_locked`, `profile_support`.
`recording.profile` сохраняет профиль последнего принятого запуска записи
отдельно от текущего выбора. `preview.profile` отражает профиль просмотра.
Старые поля статуса не удалены.

`--v4l2-ctl` панели задаёт путь команды и передаётся wrapper.
Уточнение к раннему разбору: поле `PanelConfig.v4l2_ctl` в исходном снимке
уже было; отсутствовало именно подключение к CLI/config_from_args.

`--fake-cameras` подменяет только просмотр, не реальную запись.
Поддержка в этом режиме явно помечена fake; нажатие кнопки записи не
является симуляцией. В автотестах wrapper отдельно заменяется заглушкой.

Добавлено 39 тестов (37 Python/HTTP и 2 JS/DOM). Для двух JS-тестов нужен
Node.js; при его отсутствии они пропускаются. Устанавливать Node ради
работы панели не нужно: в самой панели внешние JS-зависимости отсутствуют.
JS-тесты с DOM-заглушкой не заменяют проверку в настоящем браузере.

## Состав

| Файл | Назначение |
|---|---|
| `control_panel.py` | HTTP-панель, состояния, команды, запуск wrapper |
| `panel_page.py` | HTML/JS страницы (без внешних зависимостей) |
| `record_preflight.py` | проверки камер и места перед записью |
| `record_dual_session.py` | wrapper: сессия, два рекордера, контроль места |
| `record_camera_pyav_queue.py` | существующий рекордер одной камеры |
| `preview_dual_mjpeg.py` | существующий просмотрщик, источник `PreviewApp` |
| `deploy/usv-panel.service` | unit для systemd |
| `PANEL.md` | этот документ |

Новых зависимостей нет: используются стандартная библиотека Python,
уже установленный PyAV и системный `v4l2-ctl`.

## Состояния

| Состояние | Значение |
|---|---|
| `idle` | камеры закрыты, запись не идёт |
| `preview` | обе камеры подтвердили готовность просмотра |
| `starting` | идёт запуск просмотра или записи |
| `recording` | обе камеры пишут, метаданные в состоянии `recording` |
| `stopping` | остановка и проверка файлов |
| `error` | требуется вмешательство оператора |

Переход `preview` подтверждается только после того, как обе камеры
перешли в `running` и опубликовали хотя бы один кадр. До этого
показывается `starting`. Если одна камера не открылась, ошибка
содержит её подпись, например «Правая камера: …».

`error/ack` возвращает `idle` только если:

- нет живых потоков просмотра;
- record-lock не занят;
- не найдены процессы wrapper/рекордера.

Иначе состояние остаётся `error`, а причина видна на странице.
Автоматического завершения посторонних процессов нет.

## Токен

При первом запуске создаётся файл `~/.config/usv-panel/token`
с правами `0600`. Существующий токен переиспользуется. Значение
не выводится в журнал и не попадает в URL.

Страница спрашивает токен и хранит его в `localStorage` браузера.
Все защищённые запросы передают заголовок `X-USV-Token`, включая
MJPEG-потоки и диагностический JPEG (они загружаются через `fetch`).
Прочитать токен для ввода можно командой:

    cat ~/.config/usv-panel/token

Токен — единственная защита панели. Не публикуйте порт 8088 в
интернет и не пересылайте токен в мессенджерах. Сеть и межсетевой
экран этим проектом не настраиваются.

## HTTP-контракт

| Метод и путь | Назначение |
|---|---|
| `GET /` | страница панели (без токена) |
| `GET /api/status` | снимок состояния, нужен токен |
| `GET /stream/left.mjpg`, `/stream/right.mjpg` | MJPEG, только в `preview` |
| `GET /diagnostics/frame.jpg?camera=left\|right` | один JPEG, только в `preview` |
| `POST /api/preview/start` | включить просмотр обеих камер |
| `POST /api/preview/stop` | остановить просмотр |
| `POST /api/record/start` | остановить просмотр и начать запись |
| `POST /api/record/stop` | остановить запись и дождаться проверки |
| `POST /api/error/ack` | сбросить ошибку после устранения причины |

Управление — только `POST` с `Content-Type: application/json`.
Проверяется `Origin`/`Sec-Fetch-Site`; произвольные команды и
удалённое выключение ОС недоступны.

`/api/status` не читает диск и не ждёт процессы: снимок собирается
из уже известных данных и публикуется целиком. Поэтому статус
доступен и в состоянии `stopping`.

## Предпусковые проверки и свободное место

Перед созданием сессии wrapper:

1. проверяет, что каталог `--output-root` доступен для записи;
2. требует не меньше `--min-free-mib` (по умолчанию 4096 MiB);
3. проверяет, что устройства не открыты другими процессами
   (диагностика через `/proc`);
4. устанавливает выбранное `exposure_dynamic_framerate` на обеих камерах (default 0);
5. читает значение обратно и требует `0` на обеих камерах.

Установка и чтение выполняются ограниченными по времени вызовами
`v4l2-ctl` (`shell=False`). Другие настройки камер не изменяются.
Ошибка установки, ошибка чтения или значение, отличное от `0`, на
любой камере отменяют запуск записи обеих камер: сессия не создаётся.

**Проверки монтирования внешнего накопителя в реализации нет.**
Панель и wrapper не сравнивают файловую систему `--output-root`
с ожидаемым устройством и не отказывают в запуске, если внешний диск
не смонтирован. В этом случае каталог может быть создан на корневой
ФС, и запись начнётся туда. Поэтому перед записью оператор обязан
сам убедиться, что накопитель смонтирован:

    findmnt --target ~/recordings

Если для записи выбран внешний накопитель, перед запуском
убедитесь, что output-root находится на ожидаемом смонтированном
устройстве, а не на корневой файловой системе.

Автоматической проверки этого соответствия пока нет.

Во время записи wrapper каждые 5 секунд проверяет свободное место.
Если оно ниже `--critical-free-mib` (по умолчанию 1024 MiB), запись
штатно останавливается с причиной `low_disk_reserve`. Если сам вызов
`disk_usage` завершился исключением, запись останавливается с
причиной `disk_check_failed`, а монитор продолжает работать.

Причина остановки (`low_disk_reserve`, `disk_check_failed`,
`duration_limit`, остановка оператором) показывается отдельно от
результата проверки целостности. Записи, логи и метаданные при этом
не удаляются.

`--seconds 0` означает «до остановки оператором». Значение по
умолчанию у CLI wrapper остаётся 35; панель явно передаёт `0`.

## Ручной запуск

На Repka, из каталога `~/recorder`:

    cd ~/recorder
    venv-pyav14/bin/python control_panel.py --host 0.0.0.0 --port 8088

В консоли появятся адрес страницы и путь к файлу токена; значение
токена не печатается. Панель занимает терминал, поэтому токен читайте
во втором SSH-сеансе — в том же терминале команда `cat` не выполнится,
пока панель работает:

    ssh <user>@<repka-ip>
    cat ~/.config/usv-panel/token

Затем откройте `http://<IP-Repka>:8088/`, введите токен и работайте
кнопками.

Полезные параметры:

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `--host`, `--port` | `0.0.0.0`, `8088` | адрес панели |
| `--output-root` | `~/recordings` | корень сессий |
| `--record-seconds` | `0` | `0` — до остановки оператором |
| `--segment-seconds` | `10` | длина сегмента MKV |
| `--min-free-mib` | `4096` | порог отказа от запуска |
| `--critical-free-mib` | `1024` | порог штатной остановки |
| `--device-left`, `--device-right` | `/dev/video2`, `/dev/video4` | устройства |
| `--token-file` | `~/.config/usv-panel/token` | файл токена |
| `--stop-wait-seconds` | `3660` | ожидание wrapper при остановке панели |

`--fake-cameras` подставляет тестовые JPEG и не открывает устройства.
Это проверка страницы и HTTP, а не V4L2/PyAV.

Остановка панели (`Ctrl+C`, SIGTERM или `systemctl stop`) сначала
останавливает просмотр, затем отправляет wrapper SIGTERM и ждёт его
до `--stop-wait-seconds`. Если wrapper не завершился за это время,
панель сообщает об ошибке и не выдаёт принудительное завершение за
успешную остановку.

## systemd

Установка (выполняет пользователь, не агент):

    sudo install -m 644 deploy/usv-panel.service /etc/systemd/system/usv-panel.service
    sudo install -D -m 644 deploy/usv-panel.service.d/20-verification-timeout.conf \
      /etc/systemd/system/usv-panel.service.d/20-verification-timeout.conf
    sudo systemctl daemon-reload
    sudo systemctl enable --now usv-panel.service
    systemctl status usv-panel.service
    journalctl -u usv-panel.service -f

Служба запускает только панель. Запись после загрузки не начинается.
Для запуска записи нужна команда оператора на странице.

Откат:

    sudo systemctl disable --now usv-panel.service
    sudo rm /etc/systemd/system/usv-panel.service
    sudo systemctl daemon-reload

`KillMode=mixed` и `TimeoutStopSec=150` в unit согласованы с базовым
бюджетом панели; для длинной проверки используется drop-in
`TimeoutStopSec=3720s`. Панель ждёт wrapper до 3660 секунд: сначала
SIGTERM получает панель, и она сама останавливает wrapper. SIGKILL
всему cgroup применяется только по истечении таймаута.
`start_new_session` у wrapper не выводит его из cgroup службы; это не
способ пережить остановку службы.

`Restart=no` выбран намеренно: после аварийного завершения панели
запись не перезапускается автоматически. При следующем ручном
запуске панель проверит record-lock и процессы и, если wrapper ещё
жив, покажет `error`, а не `idle`.

## Что происходит при аварии

- Закрытие браузера или потеря Wi-Fi не останавливают запись.
- Панель и запись не используют PID/session-файлы и не выполняют
  adoption: панель управляет только запущенным ею процессом wrapper.
- Если процесс панели убит без штатного завершения (например,
  `SIGKILL` или падение интерпретатора), wrapper и рекордеры могут
  продолжить работу, но панель больше не сможет их корректно
  остановить. Сохранность записи в этом случае не гарантируется.
- `systemctl stop` ждёт панель; панель ждёт wrapper. Только после
  `TimeoutStopSec` systemd может принудительно завершить cgroup,
  и тогда запись может остаться незавершённой.

## Чек-лист первого запуска

1. **Просмотр.** Нажмите «Включить просмотр обеих камер». Дождитесь
   состояния «просмотр» и изображения с обеих камер. Если показана
   ошибка одной камеры, проверьте устройство и занятость.
2. **Запись.** Нажмите «Начать запись обеих камер». Просмотр
   остановится, состояние перейдёт в «запись». Убедитесь, что
   появились сессия, `cam-left/`, `cam-right/` и растут MKV.
3. **Статус.** Обновите страницу или откройте её с телефона: статус
   должен оставаться «запись», сессия и размеры — обновляться.
   Закройте браузер: запись должна продолжаться.
4. **Остановка.** Нажмите «Остановить запись». Дождитесь состояния
   «остановка и проверка», затем итога.
5. **Результат.** Проверьте, что итог `ok`, проверка файлов —
   `verified` для обеих камер, причина остановки показана отдельно.
   Код wrapper `0`; при принудительном завершении итог будет `error`.

## Проверки и ограничения

Локально без камер проверяются:

    python -m compileall control_panel.py panel_page.py record_profiles.py record_preflight.py \
      record_dual_session.py record_camera_pyav_queue.py tests
    python -m unittest discover -s tests -v
    bash -n test_dual_pyav_queue.sh

Тесты используют заглушки wrapper, тестовые кадры и временные
каталоги. Они не проверяют V4L2, USB, PyAV, накопитель, реальную
частоту кадров и поведение при потере питания.

Проверки монтирования внешнего накопителя нет: отсутствие монтирования
не обнаруживается автоматически и не отменяет запуск записи. Это
остаётся ручной проверкой оператора (см. `findmnt` выше).

На Repka необходимо проверить: открытие обеих камер, отсутствие
занятости устройств, установку выбранного `exposure_dynamic_framerate` и чтение
обратно, фактическую запись и `verified`, остановку по кнопке,
остановку по `systemctl stop`, поведение при заполнении накопителя
и после перезагрузки.

## Перенос файлов

С Windows на Repka (пример; подставьте пользователя и адрес):

    scp control_panel.py panel_page.py record_profiles.py record_preflight.py `
        record_dual_session.py record_camera_pyav_queue.py `
        preview_dual_mjpeg.py PANEL.md RECORDING.md `
        '<user>@<repka-ip>:~/recorder/'
    scp deploy/usv-panel.service '<user>@<repka-ip>:~/recorder/deploy/'

`tests/` на Repka не обязателен: он предназначен для локальных
проверок без оборудования. Каталог `~/recorder/deploy` нужно создать
заранее, если его нет.
