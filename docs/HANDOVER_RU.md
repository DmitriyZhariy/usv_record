## 2. Краткая памятка оператора

- Подать штатное питание, дождаться загрузки. Служба поднимает веб-панель, но не начинает запись и не открывает камеры автоматически.
- Подключить ноутбук/телефон к доступной сети установки. Последний использовавшийся адрес — http://10.16.55.1:8099/; адрес не зафиксирован данной службой и при смене сети может измениться.
- Открыть панель и ввести переданный отдельно токен. При необходимости получить его на самой Repka из /root/.config/usv-panel/token. Не помещать токен в адресную строку, GitHub или этот документ.
- Дождаться проверки режимов. Для контрольного запуска выбрать 1280x720@30, dynamic=0 и 10 либо 30 секунд; нажать «Применить профиль». После перезапуска начальный профиль снова 1280x720@60, dynamic=0; начальный предел записи в установленной службе — 0, до ручной остановки.
- Проверить изображение с обеих камер. Нажать запись; отдельный просмотр остановится, после запуска рекордеров изображения поступают уже из них с частотой до 2 кадров/с.
- Остановить запись кнопкой и дождаться окончания проверки. Успешный результат: обе камеры verified, код wrapper 0, принудительное завершение отсутствует.
- Перед выключением дождаться завершения записи и проверки, затем выполнить systemctl poweroff. Не отключать питание по одному факту исчезновения картинки или SSH.

Статическая подпись «Профиль применён. Камеры не открывались» относится к операции применения, а не обязательно к текущему состоянию после последующего запуска. Источник потока и состояние камеры проверяются отдельно. [file:469]

## 4. Профили камер и ограничения

| Профили, включённые в ПО | Статус применения |
| --- | --- |
| 1920x1080@60 | Перечислен в коде, но совместный запуск вызывал ENOSPC при резервировании USB-полосы. Исключён из согласованной эксплуатации; восстановление после отказа не считается исправленным. |
| 1280x720@60 | Есть успешная длительная сессия с обеими verified после увеличения таймаутов. Для данных той сцены измерено около 59.6 пак/с. |
| 1280x720@30 | Есть успешные короткие записи и цикл просмотр → запись → просмотр. Ранний длинный запуск был прерван таймаутом проверки; это не автоматически verified-сессия. |
| 800x600@60; 800x600@30; 640x480@60; 640x480@30 | Варианты в ПО. Отдельного протокола полевой приёмки каждого из них в переданном снимке нет. |

Подтверждение списка форматов означает, что обе камеры объявили MJPG, размер и частоту в Discrete-перечислении. Оно не доказывает устойчивую совместную работу. Допуск сравнения заявленного FPS — 0.5; пользовательские комбинации не округляются скрыто до разрешённых. Stepwise/Continuous считается ограничением парсера, а не доказанным отсутствием режима. YUYV не реализован. [file:469]

Dynamic=0 запрещает предусмотренное контролом снижение частоты; dynamic=1 разрешает его, но не гарантирует ни снижения FPS, ни увеличения яркости. При запуске wrapper устанавливает выбранное значение на обеих камерах и читает обратно. Одиночный рекордер дополнительно проверяет совпадение. Фактический темп измеряется по приёму пакетов, номинальный FPS после открытия независимо не подтверждается. [file:469]

Основной путь одной камеры: V4L2/PyAV → собственная bytes-копия пакета → очередь → поток записи → MKV + frames.csv. Пакеты, принятые в очередь, не отбрасываются молча; переполнение отражается как ошибка и останавливает запись. Отдельная копия для просмотра может быть пропущена, если её слот занят: это не пропуск из очереди MKV. [file:469]

При запуске записи из просмотра панель сначала завершает отдельный захват. Во время записи HTTP получает изображения из рекордеров, без повторного открытия камер. При отказе канала просмотра запись может продолжаться; предупреждение и возраст изображения необходимо отличать от состояния записи. Закрытие браузера не является командой остановки. [file:469]

## 6. Автозапуск, управление и безопасная остановка

Фактически установленная служба usv-panel.service включена в автозагрузку; источник /etc/systemd/system/usv-panel.service. Дополнительная настройка: /etc/systemd/system/usv-panel.service.d/20-verification-timeout.conf. По проверке 28.10.2026 служба активна, drop-in применён, TimeoutStopUSec=1 ч 2 мин; каталог кода тогда назывался /root/usv-release-e8d15fb и переименован в /root/usv_record. Служба запускается как root. Restart=no: автоматическое восстановление после аварийного падения не настроено. Запись после загрузки автоматически не начинается. [file:469]

```text
/root/recorder/venv-pyav14/bin/python /root/usv_record/control_panel.py --host 0.0.0.0 --port 8099 --device-left /dev/video2 --device-right /dev/video4 --output-root /root/recordings --record-seconds 0
```

```text
systemctl status usv-panel.service --no-pager -l
systemctl is-enabled usv-panel.service
journalctl -u usv-panel.service -n 100 --no-pager
```

Не запускать второй экземпляр панели вручную поверх службы. Для обслуживания сначала завершить запись через UI и дождаться результата, затем остановить службу. Перед отключением питания завершить ОС штатно. Команды ниже предназначены для оператора, не выполнялись при подготовке этого документа.

```text
systemctl stop usv-panel.service
systemctl start usv-panel.service
# Только после завершения записи и проверки:
systemctl poweroff
```

| Ограничение | Фактическое значение |
| --- | --- |
| Wrapper: ожидание остановки рекордеров | STOP_GRACE_SECONDS = 3600 секунд |
| Wrapper: ожидание второй камеры после чистого выхода первой | EXIT_GRACE_SECONDS = 3600 секунд |
| Панель при завершении | STOP_WAIT_SECONDS = 3660 секунд |
| systemd, итог с учётом drop-in | TimeoutStopSec = 3720 секунд (1 час 2 минуты); исходный unit без drop-in содержит 150 секунд |
| Очередь писателя при штатном завершении захвата | Отдельное ожидание writer.join — 30 секунд, затем ошибка при незавершённом потоке |

Увеличенные значения — предельные бюджеты ожидания, а не обязательная пауза. Они не доказывают достаточность одного часа для проверки записи любой длительности. Systemd использует KillMode=mixed; при исчерпании его бюджета возможна принудительная остановка процессов. Не заменять эту конфигурацию старым unit из GitHub с портом 8088 и меньшим таймаутом. ## 7. Структура сохраняемых данных

```text
/root/recordings/<UTC YYYYMMDD_HHMMSS_microseconds>/
    cam-left/
        cam_left_segment_0000.mkv
        cam_left_segment_0001.mkv
        frames.csv
        session_metadata.json
    cam-right/
        cam_right_segment_0000.mkv
        ...
        frames.csv
        session_metadata.json
    cam-left.log
    cam-right.log
```

Wrapper создаёт только корень сессии и логи. Каждый рекордер сам создаёт каталог камеры с запретом перезаписи существующего каталога. При совпадении имени сессии wrapper добавляет числовой суффикс. Записи каждой камеры и их CSV/JSON должны передаваться вместе. Логи нужны для разбора ошибок. [file:469]

MKV содержит исходные сжатые MJPEG-пакеты. CSV — индекс этих пакетов, не таблица результатов распознавания объектов. Число пакетов не следует без проверки декодирования выдавать за число визуально корректных изображений. Сегменты двух камер не являются аппаратно синхронными парами. [file:469]

## 9. Временные шкалы и сопоставление камер

Локальная выходная метка рассчитывается как floor((host_receive_monotonic_ns − segment_origin_monotonic_ns) / 1 000 000), в миллисекундах. time_base выхода — 1/1000 секунды. При чтении MKV нужно учитывать фактическую time_base пакета/потока, а не считать голый PTS абсолютным временем. [file:469]

Для оценки интервалов и сопоставления двух камер в одном запуске ОС использовать host_receive_monotonic_ns. Не сравнивать равные frame_id двух камер как синхронные экспозиции. Монотонные метки нельзя напрямую сравнивать между перезагрузками или разными устройствами. Для привязки к внешним журналам использовать host_receive_utc_ns с учётом качества синхронизации системных часов. [file:469]

Обе host_receive-метки измеряют время получения пакета на хосте после внутренних задержек камеры/USB/драйвера. Они не являются временем экспозиции. Аппаратный триггер, точная межкамерная синхронизация, внешняя навигация и калибровочные матрицы в этом ПО не реализованы. Перед рейсом проверить date -Is и timedatectl status. [file:469]

## 10. Метаданные, статусы и смысл verified

| Группа JSON | Содержание |
| --- | --- |
| Идентификация и среда | camera_id, device, started_at_utc, finished_at_utc, pyav_version, ffmpeg_libraries. |
| Запрос и открытие | requested_mode; развёрнутый profile; confirmed_camera_controls; negotiated_mode. Поле nominal FPS в negotiated_mode.fps остаётся null. |
| Время и лимиты | timestamp_policy, timestamp_is_exposure_time=false, source_timestamp_policy, segment_seconds_requested, queue_limits. |
| Приём и очередь | observed_packets, accepted_packets, measured_capture_fps, queue_overflows, rejected_frame_id при переполнении, фактические high-water значения. |
| Писатель | writer.segments, writer.written_packets, максимальные queue/mux задержки, error/close_error при наличии; writer_thread_still_alive. |
| Просмотр при записи | recording_preview: enabled, fps_limit, число публикаций/пропусков, error и признак живого потока, когда доступно. |
| Проверка | verification со списком сегментов и counts_match, payload_match, pts_match, keyflags_match; capture_error/verification_error при наличии; status и stop_reason. |

Поля появляются по мере работы. Исходный JSON обновляется через временный файл и замену. Успешный финальный рекордер возвращает код 0 только при status=verified; wrapper возвращает 0 только при успешном завершении обеих камер без принудительного завершения. Нормальная причина duration_limit или user_stop сама по себе не является ошибкой. [file:469]

Текущий нюанс реализации: перед полной проверкой в JSON временно записывается status=failed. Поэтому failed без finished_at_utc после принудительного завершения может означать оборванную проверку, а не установленное повреждение всех сегментов. Нельзя вручную менять такой статус на verified: нужна завершённая проверка. [file:469]

verified подтверждает сопоставление принятых пакетов с CSV и перечитанными MKV: порядок/количество, SHA-256 payload, PTS и keyframe-признаки. Он не доказывает отсутствие потерь до приложения, правильную экспозицию, резкость, геометрическую калибровку, синхронность камер или возможность декодирования каждого изображения. Проверка не декодирует видео целиком. [file:469]

## 11. Долгая остановка и известные ограничения

- После остановки сначала дренируется очередь и закрываются MKV/CSV, затем все сегменты перечитываются и сверяются. Длительность проверки зависит от объёма данных и производительности; нормальная остановка может занимать минуты.
- Ранний предел wrapper 35 секунд прервал проверку десятиминутной сессии на 18 из 61 сегмента каждой камеры. Увеличение таймаутов позволило последующему длительному запуску завершиться с verified; это не гарантия для произвольно больших записей.
- Полное пропадание питания, зависание demux или SIGKILL не гарантируют сохранность последнего сегмента/CSV. Десятисекундная сегментация уменьшает область риска, но не даёт обещания нулевой потери данных.
- Профиль не сохраняется между перезапусками; после загрузки его нужно выбрать заново. Начальная длительность 0 означает ручную остановку, а не десятисекундный тест.
- Подключение внешнего диска не меняет --output-root автоматически. Сейчас служба пишет в /root/recordings. Проверка монтирования внешнего накопителя отсутствует.
- Операции чтения записей для выгрузки/проверки конкурируют за ресурсы. Плановое копирование выполнять после завершения записи и её проверки.
- При ошибках занятости не запускать второй захват и не применять kill -9 или выгрузку драйвера как обычный способ остановки. Сначала диагностировать владельцев устройств.
